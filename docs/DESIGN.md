# 제로가계부 설계도

> 이 문서는 살아있는 설계도다. 결정이 바뀌면 문서를 먼저 고친다.
> ✅ = 구현됨 · 🔨 = 설계 확정, 미구현 · ❓ = 미결정 (문서 끝 "열린 질문" 참고)

## 1. 제품 원칙

**"목표를 향해 잘 가고 있는지 알려주는 나침반."**
절약 → 저축 → 자산 증식이 목적이고 기록은 수단이다.

기능을 넣을지 뺄지 흔들릴 때의 판단 기준:

1. **3초 입력** — 기록의 마찰을 늘리는 변경은 하지 않는다. 상세함은 나중에 보강하는 구조로.
2. **안도 또는 교정** — 모든 화면은 "잘 가고 있어요" 혹은 "여기서 벗어났어요" 중 하나를 말해야 한다. 중립적인 숫자 나열은 실패다.
3. **함께 쓰는 장부** — 데이터 설계는 항상 "부부 2명이 같은 장부"를 기본 시나리오로 검증한다.
4. **내 데이터는 내 것** — 오프라인에서 완전 동작, 언제든 내보내기, 탈퇴하면 깨끗이 삭제.

## 2. 출시 목표와 품질 기준

**처음부터 스토어(App Store / Play Store) 공개를 목표로 설계한다.**
따라서 다음은 "나중에"가 아니라 출시 전 필수다:

- UGC(피드) 신고·차단 — Apple 심사 필수 요건 (Guideline 1.2)
- 개인정보처리방침 + 계정 탈퇴(데이터 삭제) — 양대 스토어 필수
- 크래시 리포팅(Sentry) — 남의 폰에서 죽는 걸 알 수 있어야 함
- 온보딩 — 설명 없이도 3분 안에 첫 기록과 첫 목표까지

## 3. 유저 여정

### 3.1 첫 실행 (온보딩) 🔨
```
가치 소개(2~3장: 기록→목표→함께)
 → 이번 달 저축 목표 설정 (스킵 가능)
 → 저녁 리마인더 알림 허용 (스킵 가능)
 → 카카오/이메일 로그인 or "나중에" (로컬 모드)
 → 홈
```
원칙: 어떤 단계도 강제하지 않는다. 로그인 없이 끝까지 쓸 수 있다.

### 3.2 매일의 사이클 ✅(입력) / 🔨(알림)
- 결제 직후: 알림 or 앱 열기 → 3초 입력 (금액→카테고리→저장)
- 저녁 리마인더 알림 탭 → **바로 입력 화면으로 딥링크** (`zerobudget://transaction/new`)
- 홈에서 목표 진행률 확인 → 안도/교정 메시지

### 3.3 부부 합류 ✅(코드) / 🔨(병합)
초대 코드 발급 → 배우자 입력 → 같은 장부 멤버 → 서로의 기록이 실시간 합쳐짐.
합류 시 기존 기록이 있으면 **병합 마법사**(§5.3)를 띄운다.

### 3.4 월말 사이클 🔨
월이 바뀌면: 지난달 결산 카드(목표 달성 여부, 카테고리 하이라이트) → 이번 달 목표 설정 유도 → 자랑하기 제안 ("지난달 목표 달성을 피드에 공유할까요?")

## 4. 화면 맵

```
(tabs)
 ├ 홈: 목표 카드 → 요약 → [거래 입력·자랑하기] → 내 이야기 → 피드   ✅
 ├ 내역: 월 리스트 ↔ 캘린더                                        ✅
 ├ 통계: 도넛 + 6개월 추이                                          ✅
 └ 설정: 계정/동기화, 자산, 카테고리🔨, 반복거래🔨, 부부, 친구🔨,
         알림🔨, 내보내기🔨, 탈퇴🔨

모달: 거래 입력/상세 ✅ · 목표 설정 ✅ · 자랑하기 ✅ · 로그인 ✅
     온보딩 🔨 · 병합 마법사 🔨 · 월말 결산 🔨
```

## 5. 데이터 설계

### 5.1 현재 테이블 ✅
`ledgers / ledger_members / categories / accounts / transactions / goals / budgets(예약)`
— 전부 ledger 소속, 기기 생성 uuid, soft delete, dirty 플래그. 서버는 동일 구조 + RLS.

### 5.2 추가 테이블 🔨

**recurring_rules** (반복/고정 거래 — 로컬+서버 동기화 대상)
```
id, ledger_id, user_id, type(income|expense), amount, category_id,
account_id, memo, frequency('monthly'|'weekly'),
day_of_month(1~31, 말일=31 처리) | weekday(0~6),
start_on, end_on(null=무기한), sync 공통 컬럼
```
생성 방식: 앱 실행/포그라운드 시 로컬에서 due 항목을 거래로 생성.
**부부 양쪽 기기가 동시에 생성해도 중복되지 않도록, 생성 거래의 id를
`uuidv5(rule_id + occurred_on)`처럼 결정적으로 만든다** → 같은 id로 upsert되어 자연 dedup.

**profiles** (서버 전용)
```
id(=auth.users.id), nickname(unique, 필수), created_at, updated_at
```
피드 노출 이름은 이메일이 아니라 닉네임. 가입 직후 닉네임 설정 화면.

**friendships** (서버 전용) — 친구도 초대 코드 방식(연락처 접근 없음)
```
id, user_id, friend_id, status('accepted'), created_at   -- 코드 입력 즉시 수락
```

**posts 확장**: `visibility('friends'|'public')` 추가. 기본값 friends.

**reports / blocks** (서버 전용)
```
reports: id, reporter_id, post_id, reason, created_at
blocks:  id, user_id, blocked_user_id, created_at
```

### 5.3 데이터 병합 정책 🔨 — "항상 물어보기"

트리거 두 가지:
- **재로그인/새 기기**: 로그인했더니 서버에 이미 내 장부가 있고, 로컬 장부에도 기록이 있음
- **부부 합류**: 상대 장부로 전환하는데 내 기존 장부에 기록이 있음

병합 마법사가 3지선다를 묻는다:

| 선택 | 동작 |
|---|---|
| **합치기** | 거래를 대상 장부로 이전(`ledger_id` 재지정 + dirty). 카테고리는 **이름+타입으로 매칭**, 없으면 대상 장부에 생성. 자산도 동일. 목표는 대상 장부 것 우선(충돌 월은 묻기) |
| **보관** | 기존 장부를 그대로 두고 현재 장부만 전환. 설정에서 장부 전환으로 언제든 열람 |
| **삭제** | 기존 장부 soft delete (30일 내 복구 가능 안내) |

### 5.4 예산 계층 ❓
연간 목표 → 월 목표 → (2단계) 카테고리별 예산(budgets). 연간 목표의 스키마/UX는 미결정.

## 6. 동기화 프로토콜

### 6.1 현재 구현 ✅
- **push**: dirty=1 행을 청크 upsert → 성공 시 updated_at 불변인 행만 dirty 해제
- **pull**: 테이블별 updated_at 커서, 페이지네이션, LWW(로컬이 dirty이고 더 최신이면 유지)
- **트리거**: 로그인, 포그라운드, 수동. 실패해도 dirty가 유지되므로 다음 트리거가 자연 재시도
- **멤버십 변경 시** 커서 리셋 → 전체 재-pull ✅

### 6.2 보강 🔨
- **시계 왜곡 대응**: LWW가 클라이언트 시계에 의존하는 한계 → 서버 트리거로 `updated_at = greatest(now(), client값)` 보정. 극단적으로 미래 시각인 클라이언트 값은 서버 now()로 클램프
- **쓰기 후 debounce push** (지금은 포그라운드 트리거뿐): 마지막 쓰기 3~5초 후 자동 push
- **동기화 상태 UI**: 설정의 "지금 동기화" 외에, 실패 지속 시 홈에 조용한 배너 1줄

## 7. 소셜 설계

### 7.1 공개 범위 — 기본 친구, 선택적 전체공개
- 글 작성 시 공개 범위 선택: **친구(기본)** / 전체공개
- 피드 구성: 친구 글 + 전체공개 글(탭 또는 섞어서 ❓)
- 부부는 자동 친구
- RLS: `visibility='public'` 이거나 작성자가 나와 friendships로 연결된 경우만 select

### 7.2 안전 (스토어 필수) 🔨
- 글마다 **신고** 버튼(사유 선택) / 작성자 **차단**(그 사람 글 전부 숨김, blocks 테이블 + 클라이언트 필터)
- 신고 N건 누적 시 자동 숨김 + 운영자 확인 (초기엔 수동 운영)
- 금칙어 1차 필터(클라이언트) — 완벽하지 않아도 심사 요건 충족용
- 닉네임 노출만 허용, 이메일/실명 노출 금지

## 8. 보안 · 프라이버시

- **RLS가 유일한 방어선** — 모든 테이블 정책 존재 ✅. 출시 전 익명/타인 계정으로 접근 시도하는 테스트 시나리오 작성 🔨
- **계정 탈퇴** 🔨: `delete_account()` RPC — 내 posts/reports/profiles/friendships 삭제, 내 멤버십 삭제. 장부는 **다른 멤버가 남아 있으면 유지**(부부 데이터 보호), 마지막 멤버면 장부째 삭제 ❓(확정 필요)
- **내보내기** 🔨: 설정에서 CSV(거래 전체) 공유 시트로 내보내기. 서버 불필요, 로컬에서 생성
- **개인정보처리방침** 🔨: 수집 항목(이메일, 닉네임, 거래 기록), 보관/파기, 처리 위탁(Supabase) 명시. 호스팅된 URL 필요(스토어 요건)

## 9. 품질 · 운영 🔨

- **크래시 리포팅**: sentry-expo. 개인정보(금액/메모)는 breadcrumb에서 제외
- **빌드/배포**: EAS Build + Submit. `app.json`에 bundleIdentifier/package 확정 필요 ❓
- **OTA 업데이트**: expo-updates로 JS 핫픽스 채널
- **테스트 전략**: 순수 로직(집계/목표/동기화/병합)은 jest ✅ 유지 · 병합 마법사와 동기화는 시나리오 테스트 추가 · 출시 전 실기기 체크리스트
- **성능**: 거래 1만 건 기준 리스트/통계 쿼리 확인 (인덱스는 있음 ✅)
- **접근성/다크모드**: 다크모드는 v1.0 범위 ❓
